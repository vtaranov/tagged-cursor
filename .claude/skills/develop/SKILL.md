# Разработка требований

Аргумент: номера (`/develop 3`, `/develop 3 5 7`) или группа (`/develop group appearance`).

1. **Подготовка.**
   - `git status` должен быть чистым; иначе выясни у пользователя, что с изменениями.
   - Прочитай требования и `CLAUDE.md`. Требования без анализа (`new`) — сначала короткий анализ по навыку `analyze`.
   - Если решение неочевидно или есть риск регрессий — покажи план и дождись согласия. Однозначные — делай сразу.
   - `python3 scripts/backlog.py set status in-progress <ids>`.
2. **Реализация.** Стиль кода — как в соседних файлах, комментарии только для неочевидного. Особенности приложений из `CLAUDE.md` не ломать.
3. **Сборка и установка.** `./install.sh`, убедиться по логу, что приложение запустилось (есть записи о поиске курсора).
4. **Проверка пользователем.** `set status testing`. Дай сценарий проверки из «Плана» — коротким списком — и спроси про регрессии в затронутых приложениях из `docs/test-matrix.md`. Дождись ответа. Проблемы — исправляй и повторяй шаг 3–4.
5. **Закрытие** (после подтверждения пользователя):
   - убрать временную диагностику;
   - «Итог» в каждом требовании: что сделано, версия, что осталось (остаток — новое требование через навык `req`);
   - `set status done`;
   - версия в `Info.plist` (`plutil -replace CFBundleShortVersionString -string X.Y.Z Info.plist`, `CFBundleVersion` +1): minor — новое поведение, patch — исправления;
   - запись в `CHANGELOG.md`;
   - новые особенности приложений — в `CLAUDE.md`, новые сценарии — в `docs/test-matrix.md`;
   - `./install.sh` финальной версии;
   - `git add -A && git commit -m "vX.Y.Z: <кратко> (#id, #id)"`.
6. Итог пользователю: версия, что вошло, рекомендация следующего шага по очереди.
