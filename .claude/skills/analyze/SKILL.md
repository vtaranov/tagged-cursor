# Анализ требований

Аргумент: номера требований (`/analyze 3 5`) или группа (`/analyze group remote`). Без аргумента — все `new` с приоритетом `high`.

Для каждого требования:

1. Прочитай его (`python3 scripts/backlog.py show <id>`), `CLAUDE.md` (особенно «Особенности приложений» и «Запреты») и затронутый код.
2. Выясни причину или суть. Если нужны данные о поведении приложения:
   - временная диагностика уровнем `notice`, `./install.sh`, короткий сценарий для пользователя, чтение `/usr/bin/log show … --predicate 'subsystem == "local.tagged-cursor"'`;
   - никогда не логировать нажатия и символы; не делать тяжёлых AX-запросов к Office;
   - временную диагностику после анализа убрать или явно пометить в требовании, что она осталась.
3. Заполни «Анализ»: причина/суть; 1–3 варианта с рекомендацией; риски (регрессии в каких приложениях, CPU, разрешения); зависимости от других требований.
4. Заполни «План»: шаги реализации и **сценарий проверки для пользователя** (конкретные приложения и действия, локально и/или через Screen Sharing).
5. Выстави `size` (S/M/L), при необходимости скорректируй `priority`/`group`, `status: analyzed` (или `rejected`/`deferred` с причиной в «Итоге», если делать не стоит — согласуй с пользователем).

В конце: сводка по требованиям в 2–4 строки каждое, рекомендация — что и какой группой брать в `/develop`. Закоммить изменения backlog (и снятие диагностики, если было): `git commit -m "backlog: анализ #id…"`.
